# TDU VR (SteamVR, 6DOF)

A `d3d9.dll` proxy for Test Drive Unlimited (PC, 2007 exe). It puts the game in a headset through SteamVR with full 6DOF head tracking and stereo.

## How it works
- The game's vertex shaders carry D3DX constant tables (`gVSWorldViewProject`, `gVSWorldView`, `gView`, `gViewProject`, `gProj`, `gInvView`, ...). The proxy reads them in `CreateVertexShader`, then rewrites those registers before every draw:
  - `*View` → `M * invEye`
  - `*ViewProj` → `M * inv(P) * invEye * Peye`
  - `Proj` → `Peye`
  - `InvView` → `E * M`
- **`P` is worked out per draw.** TDU draws different parts of the scene with different depth ranges (for example near 2 m with infinite far, and near 0.8 m with far 40 km) and changes FOV between views. So one shared projection is wrong.
  - With a matrix pair, it's exact: `inv(WorldView) * WorldViewProj`, or `inv(View) * ViewProj`.
  - With only a combined matrix, the depth terms are recovered from that matrix and the FOV comes from the main camera.
  - 2D and orthographic draws fail these checks and are left alone.
- **`Peye` is the headset's off-center frustum**, with the draw's own depth range kept. TDU's camera is right-handed and looks down −Z.
- **Only main-view passes are rewritten:** the render target must have the back buffer's shape and the viewport must be (nearly) full. Cube maps, shadow maps, mirrors and menu car previews are skipped.
- **2D draws go onto a virtual screen.** Menus, HUD and cursor are flat draws with orthographic matrices. They're moved onto a flat screen fixed in front of you (`UiFov` wide, `UiDistance` away, recentered with F8) and projected correctly for each eye. Without this, the same picture lands on different directions in each off-center eye image and you see it double. Post-processing quads read the game's render targets, so they're recognized and left full-frame.
  - The game layers its menus with the depth test (tiny z values, buttons in front of the bars behind them), so the screen keeps each draw's own depth. Flattening it hid the bottom-bar buttons ("Wyjście", "Powrót", ...).
  - In menus the game never clears the frame, because its full-screen background normally covers it. On the virtual screen that background covers only part of the frame, so the mod clears the frame after each Present. Otherwise the other eye's older image showed through as a second menu.
- **Head look.** The game has TrackIR head-look built in: it reads a yaw and pitch, clamps them, and turns its in-car camera. The mod writes the headset's yaw and pitch there each frame, at addresses checked against this exe's camera code before use, so the in-car camera points where you look. The rewrite then removes exactly that rotation and only adds roll, position and eye offset.
  - Why: the game runs a sphere-cull test (0x50b3b0) against the in-car camera for a handful of objects per frame, about 44° either side of where that camera looks; head look keeps it centered on your view. The rest of the world does not depend on the camera's direction or FOV (tested: with the camera turned 86° away, or its FOV forced to 10°, everything ahead is still drawn).
  - Measured on the in-car camera: angles apply on the next frame with no smoothing; yaw is clamped at 97° and pitch at 30°; the game's pitch sign is inverted.
  - The camera looks 4.7° down and yaws around the car's up axis. The mod splits the head pose in that same frame.
  - The game skips its camera update on roughly 1 in 9 frames. So the mod reads the angles the camera actually used back from the camera object at the first draw of each frame, and corrects the eye matrices if they differ. The object is found by a short memory scan while a tiny, changing look is fed (under 0.05°). Until then, and whenever that camera stops following (menus, other camera views), no rotation is taken out, so head tracking works normally there.
  - The first-draw readback is not always what gets rendered. While the head turns, about 15% of the frames that start a pair (the left eye) are drawn with the previous frame's camera, although the camera object already holds the new one (never seen on right-eye frames). So the mod finds the camera each frame was actually drawn with and matches it by orientation against the camera object's state now and at the last 4 first draws (`+0x70`), then uses that state's look.
  - That camera must be known before the world is drawn. The game's own `InvView`/`View` only shows up about 1,100 draws into the frame, after the roads, trees and buildings. Matching there left all of those 1–3° off on those left-eye frames: ghosting and trailing while turning the head. So the camera is read from the first draw whose world matrix doesn't rotate (ground pieces; in the car, the very first 3D draw). Its `WorldView` 3x3 rows are the view rotation's, scaled. The pick is checked once more at the first `InvView`/`View`.
  - The match allows about 1°: while driving, the game sometimes draws a state from between two first draws (the car has moved a little), and while the head turns the looks to choose from differ by more than that.
  - Log line `head look:` shows: `rendered with another look than read` (frames corrected, per eye), `unmatched` (no exact match; the nearest state within 1° is used), `known by 3D draw` (should be about 0) and `early pick corrected` (should stay 0).
  - The menu/HUD screen stays fixed in front of you; it doesn't turn with the game camera.
- **Positions never depend on noisy depth terms.** Per-draw depth terms carry float noise (the near plane wanders by about 1.5%). WorldView is rebuilt from WorldViewProj using only the FOV scales, so the depth terms only affect depth. They're snapped to the frame's few real depth ranges, so each range gets one bit-identical frustum.
- **Stereo is alternate-eye rendering:** even frames are rendered for one eye, odd frames for the other. Both frames of a pair use the same head pose, and the presenter only shows a left/right pair from the same pair. So it doesn't matter whether SteamVR reprojects each eye with its own pose or with one shared pose. Each eye therefore gets a new image at half the game's frame rate: the game's FPS is what decides how smooth it feels, not the 90 Hz the headset shows.
- **The frames stay on the GPU (`GpuCopy=1`).** The game's Direct3D 9 runs on a Direct3D 12 device of the mod's (Windows' D3D9On12). At each Present the back buffer is copied into an eye image on the GPU, and the presenter hands those D3D12 textures straight to SteamVR. The old CPU copy took the game from about 150 to about 85 fps at 2560x1440: `GetRenderTargetData` makes the game wait for the GPU every frame, plus 15 MB per frame through system memory.
  - The game window on the desktop stops updating in this mode: D3D9On12's Present to a window blocked for ~300 ms on every other frame (6 fps), and the headset doesn't need it. Use SteamVR's mirror window to watch.
  - Taking a frame out of 9On12 (`UnwrapUnderlyingResource`) makes the game thread wait until 9On12's worker thread has caught up, about 2 ms, whichever frame it is. So both eyes of a pair are taken out together, after the right eye: the headset can't show a pair before its right eye anyway, and the wait comes once per pair.
  - 9On12 records the game's calls into one of two 768 KB buffers, and its worker thread turns them into D3D12. When a buffer is full, the game waits for the worker. Every `SetVertexShaderConstantF` of up to 16 registers takes a fixed 268-byte slot (17–256 registers: 4108 bytes), and TDU makes about 10,900 of them per frame, so constants alone filled the buffer about four times per frame. The mod batches them: the game's constant writes and its own matrix rewrites only update a copy, and before each draw the registers that really changed go out in windows of at most 16, about 4,800 calls per frame. State blocks (TDU records a couple) are handled: their Capture and Apply see the batched values first. `TDUVR_CONSTBATCH=0` turns it off.
  - Measured parked in the car at 2560x1440 without a headset: about 112 fps (106 before batching and the per-pair copy), p99 frame 10.5 ms. The game thread still waits on 9On12's worker for about 40% of each frame, so 9On12 itself is now the ceiling. The GPU is about 37% busy.
  - 9On12 keeps every fence it is handed back with a resource, so handing back the same render target got slower each frame (~10 ms per frame after an hour). The render targets are replaced every 1024 frames.
  - The game exe is not large-address-aware, so it has 2 GB of address space and uses ~1.7 GB with plain d3d9. The CPU copy's buffers sometimes didn't fit (in tests at 2560x1440 the game crashed about 35 s in). With 9On12 the game uses ~1.5 GB in the car. Setting the exe's large-address-aware flag doesn't work: the SecuROM-protected exe then quits before its first frame.
  - In the house the game opens a second, tiny device. It gets plain d3d9, since its Present would stall in 9On12 as well.
- **DXVK (`DXVK=1`, experimental).** The game's Direct3D 9 runs on DXVK (Vulkan) instead: `dxvk_d3d9.dll` next to the game, which is the 32-bit `d3d9.dll` of a [DXVK](https://github.com/doitsujin/dxvk) release, renamed. The eye images still reach SteamVR through Direct3D 12, the way they do on D3D9On12, so SteamVR never touches DXVK's Vulkan queue:
  - Each frame the back buffer is copied into the eye's texture of the mod's (a DXVK shared texture, which DXVK never moves in memory) and switched to `TRANSFER_SRC_OPTIMAL` through DXVK's D3D9 interop interface; the game's Present puts that on DXVK's queue.
  - One frame later, one `vkQueueSubmit` on DXVK's queue (under DXVK's queue lock, nothing else inside) copies both eyes into two D3D12 textures imported into DXVK's Vulkan device. It waits for and signals D3D12 fences shared with Vulkan, so the CPU never waits. The mod's D3D12 queue waits for that fence on the GPU and copies on into the presenter's eye images. A frame later because DXVK's flush only queues its work for its submission thread.
  - Handing SteamVR Vulkan images on DXVK's queue directly (the first try) lost the Vulkan device within seconds: `WaitGetPoses` and `PostPresentHandoff` use the queue of the last submitted texture from the presenter thread while DXVK's own thread submits to it. Making them wait for DXVK's queue lock instead stalled DXVK ~90 ms per frame with an idle headset.
  - Measured parked in the car with SteamVR running (headset idle), at 2560x1440 and full detail: about 228 fps, the eye copy 0.14 ms per frame, against about 106 with D3D9On12. That's a new image for each eye on every headset frame. The desktop window keeps updating.
  - TDU resets its video settings when the GPU it sees changes, and DXVK reports it slightly differently from Windows' d3d9 (a made-up driver version, no subsystem id, modes in another order): one test run on DXVK put the saved resolution back to the default. So on DXVK the mod answers the game's adapter identity and display-mode questions from Windows' d3d9.
- **A presenter thread feeds SteamVR.** Every headset frame, it submits the newest finished image of each eye with its render pose. So the compositor always gets a complete frame on time and only has to reproject head motion. Meanwhile the game runs at its own rate and never waits on the headset. With `GpuCopy=0` the back buffer goes through system memory with a one-frame lag instead.
- **The game's simulation runs on its own timer.** A multimedia timer calls 0x81ee50 every 10 ms (100 Hz, from the game's config), which steps cars, physics and cameras with dt = the real time since the last step (0x81dfd0). Rendering just shows whichever step finished last. Measured: the timer really runs 91 steps/s, at moments unrelated to frames. So a frame shows a state up to 11 ms old, the two eyes of a pair show different moments, and a step can land halfway through drawing a frame.
  - `SimLock=1` (experimental) stops the game's timer and steps from the mod's own thread instead. In the car, the steps run right before each new eye pair, catching up the real time since the previous pair in steps of at most 10 ms. Both eyes then show the same moment, and nothing moves while a pair is drawn. Elsewhere (menus, loading, the house) the thread calls the game's own timer callback on an exact 10 ms grid. Stepping at pairs in the main menu stopped it reacting to Enter.
- Quest via Link, Air Link or Virtual Desktop works through SteamVR. SteamVR's OpenXR runtime has no 32-bit support, so OpenVR is used.

## Install
Needs the PC version of Test Drive Unlimited (the 2007 exe this was made against), SteamVR and a headset. Quest works through Link, Air Link or Virtual Desktop.

1. Get `d3d9.dll`, `openvr_api.dll` and `tdu_vr.ini` from the release zip, or build them: run `build.bat` (needs Visual Studio with C++ tools; set `TDU_DIR` to the game folder to also test against the game's shaders).
2. Copy those three files next to `TestDriveUnlimited.exe`.
3. Start SteamVR, then the game. The mod forces windowed mode and turns V-Sync off, since the game has no options for either. If SteamVR finds no headset at that moment, the mod stays out of the way and the game runs as normal. In the house the game opens a tiny second display device (120x61). The mod leaves it alone; taking it over used to crash the game a few seconds after arriving.
4. With `AutoDrive=1` (the default) you need no menus. About 8 s after the main menu shows, the mod presses Enter ("Kontynuuj grę"), then about 10 s after the house shows, Backspace ("Wyjście"), and you're in your car, about a minute after launch. It presses keys only while the game window is in front, and stops after 5 minutes. Set `AutoDrive=0` to use the menus yourself.
5. Sit in the in-car view and press **F8** to recenter.

To uninstall, delete those three files.

## Settings that matter
Each eye gets every other game frame, so each eye's picture updates at **half the game's FPS**. Head rotation is still reprojected at the full headset rate, but everything that moves in the scene (and at speed, that's everything) only updates at half the game's FPS. That's why it can feel well below 90 even though Virtual Desktop shows 90. The status lines in `tdu_vr.log` show both: `fps` (the game) and `new pairs shown` (what each eye gets).
- `GpuCopy=1` (the default) is the biggest win: see above.
- `DXVK=1` (experimental, needs `dxvk_d3d9.dll`): about twice the frame rate of D3D9On12 in tests, so each eye can update at the headset's full rate. Not yet verified in a headset; if the headset shows nothing, set it back to 0.
- If another frame limiter or overlay hooks the game (for example framepacer), exclude `TestDriveUnlimited.exe` from it. It sits in the same Present call.

**Frame generation must be off.** Both SteamVR's **Motion Smoothing** and Virtual Desktop's **SSW** force the app to half rate and invent the in-between frames from motion. With alternate-eye images that warps, stretches and wobbles the world.

The `SteamVR:` part of the status lines in `tdu_vr.log` should read `throttled 0, motion smoothing off`. If you see `presenter 60 Hz, throttled 1, motion smoothing ACTIVE` even at an idle loading screen, one of them is still on.

- **SteamVR → Settings → Video:** turn **Motion Smoothing off**, globally or per application for this game.
- **Virtual Desktop → Streaming:** set **Synchronous Spacewarp (SSW)** to **Disabled**.
- **Headset refresh rate:** 90 or 72 Hz is easier on the GPU than 120.
- **In-game:** 1920x1080 or lower, not your desktop's 5120x1440. Lower shadows and reflections too: about 300–450 of the roughly 3,000 draws per frame go into reflection and shadow maps.

## Testing without the headset
Environment variables, set before launching the game:
- `TDUVR_NOHMD=1`: no SteamVR at all. A simulated 90 Hz Quest 3 takes its place, and everything else runs as in the headset: rewrite, GPU copy, presenter (without submitting). The log's status lines then show what the mod costs.
- `TDUVR_DRIVETEST=<seconds>`: that long after the in-car camera is found, hold the accelerator for 5 s. The `camera at` part of the log's head-look line shows whether the car moved.
- `TDUVR_FAKEHEAD=<degrees>,<seconds>`: the head looks straight ahead and turns left/right by that much once per period (`0,4` holds still). Otherwise a headset lying on the desk points anywhere.
- `TDUVR_DUMP=<file.bmp>,<seconds>`: writes one eye image exactly as sent to the headset. `,+<seconds>` counts from when the in-car camera is found. A path with `%03d` writes a numbered image every `<seconds>` instead.
- `TDUVR_PROFILE=<seconds>,<delay>`: once the in-car camera has been on screen for `<delay>` s, samples the four busiest threads at 1 kHz and writes every sample (instruction pointer and the return addresses on the stack) to `tdu_prof.txt` next to the game. `build.bat` writes `build\d3d9.map` to name the mod's own addresses.
- `TDUVR_ABTEST=<seconds>`: in the car, cycles constant batching and the per-pair copy through all four on/off combinations, `<seconds>` each, so one run compares them. Each status window says which was active.
- `TDUVR_LOOKTEST=1`: cycles fixed head-look angles and logs the camera the game produced.

With `AutoDrive=1`, a launch reaches the in-car view on its own. Keep the game window in front: the game reads the keyboard through DirectInput, so only real (injected) key presses work.

## Known limits
- **Edge culling.** Objects culled by the game's sphere test (about 44° either side of where the game camera looks) can pop at the outer edges of the headset view (up to 55° out) and past the head-look limits (97° yaw, 30° pitch). Widening the game's FOV is not a fix: its camera FOV (set at 0x404840, called from 0x8d696e) also drives level of detail, and at 120° distant signs vanish and trees switch models.
- **HUD and menu sharpness.** The virtual screen is drawn at the game's resolution and then squeezed into part of the eye image, so small text can be soft. Raising `UiFov` makes it bigger. Screen-space effects drawn as 2D with plain textures, such as lens flares, would land on the virtual screen too.
- **Alternate-eye artifacts.** At high speed, side scenery can shimmer, because each eye's image comes from a different frame.
- **Half-rate eyes.** Alternate-eye rendering gives each eye half the game's FPS. Real 90 Hz per eye needs either 180 game fps or both eyes drawn in one frame (each main-view draw issued twice, into two render targets). That's the next big step.
- **DXVK path not verified with the headset on yet.** It runs with SteamVR and an idle headset (SteamVR then shows 10 frames per second), including the hand-over to SteamVR.
- **D3D9On12 is the ceiling.** Its worker thread can't keep up during the draw-heavy part of each frame, and taking frames out costs about 2 ms per pair. Batching cut the game thread's waiting, but about 112 fps parked (roughly 56 pairs per second) is near what 9On12 allows for this game. Plain d3d9 runs it at ~150 fps but can't hand frames to SteamVR on the GPU: it can't create shareable surfaces, so neither D3D11 sharing nor OpenGL interop (`WGL_NV_DX_interop`) can read them (tested).
- **Lighting.** Per-pixel lighting, specular and mirrors use the original camera, so small errors appear when you lean far.
